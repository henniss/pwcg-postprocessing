# Research notes: pwcg-postprocessing

## What this repo is

A personal toolkit of Bash scripts that post-process missions generated by
**PWCG** (Pat Wilson's Campaign Generator) for IL-2 Sturmovik Battle of
Stalingrad / Bodenplatte before they're flown. PWCG writes a `.mission` file
(plain-text mission-editor format) plus a `.eng` subtitle file (UTF-16LE); this
repo mutates both in place to patch things PWCG itself can't do or gets wrong
(wind direction, tactical codes, escort behavior, block durability, etc.),
then hands the mission off to the game's `MissionResaver.exe` and optionally
drops it straight into the dedicated-server `.sds` config.

It's designed to run under **Cygwin on Windows** (paths use `cygpath`,
`core.bat` is a drag-and-drop launcher, dependencies are installed via the
Cygwin package manager). The author's own README calls the scripts "kind of
crap... thrown together quickly," so this is a working hobby tool, not a
polished product.

## Execution model (`core.sh`)

1. Invoked as `core.sh <path-to-.mission>` (normally via drag-and-drop onto
   `core.bat`, which shells out through `mintty`/bash).
2. Checks for `sed`, `ed`, `jq`, `iconv`, `perl` on `PATH`.
3. On first run, generates a `config.sh` template (gitignored) that the user
   must edit with real install paths (`root`, `sds`, derived `PWCGInput` /
   `PWCGCampaigns`). Validates these are real dirs/files before continuing.
4. Supports "underscore-prefixed" re-runs: dropping a mission file named
   `_Foo.mission` tells core.sh to treat it as an edited copy that should
   replace the real `Foo.*` files (used for iterating on a single mission by
   hand — see `test.sh`/`3a92ccc` in history).
5. Derives the **campaign name** from the first space-delimited token of the
   mission's filename, and only proceeds with campaign-specific features if a
   matching directory exists under `PWCGCampaigns`.
6. Parses the `.eng` subtitle file (converted from UTF-16LE) with grep/sed to
   recover semantic info PWCG doesn't expose elsewhere: the player's flight
   name, whether this is an escort mission, the escorted flight's name, and
   the home airfield — all by pattern-matching fixed English briefing phrases
   like "stationed at" and "Escorted by/Rendezvous with".
7. Sources `default_env.sh`, then an optional per-campaign `env.sh` override
   (lets you tune behavior per campaign without touching the main scripts).
8. Makes a full backup of the mission file set into `backups/` before doing
   anything.
9. Runs every `components/*.sh` file in **numeric-prefix order** inside a
   subshell. Each component defines `shouldApply` (decide whether to run) and
   `apply` (do the work); failures either just get logged (`shouldHalt=false`)
   or trigger a full restore-from-backup and abort the whole pipeline
   (`shouldHalt=true`, the default).
10. Cross-subshell "abort the loop" signaling is done through a **named
    pipe/fd** (`mkfifo` + `exec {chan}<>`) since a subshell can't set a
    variable the parent loop can see — writing `"stop"` to the fd and reading
    it with `read -u $chan -t 0` after each component.

This is a surprisingly careful piece of shell plumbing for what is otherwise a
"quick and dirty" tool — the component framework, per-campaign overrides, and
backup/restore/trash lifecycle are the most "engineered" part of the repo.

## The `components/` pipeline

Numeric prefixes = ordering; everything in a given tier is otherwise
independent and can be deleted individually (per the README) to disable a
tweak.

- **00_campaign_init.sh** — ensures `pilot-code-map.csv` and `env.sh` exist in
  the campaign directory, creating empty stubs and telling the user to edit
  them.
- **01_block_durability.sh** — rewrites every block's `Durability` value in
  the `.mission` file from a lookup table (`data/durability.csv`, block-name
  → durability, ~900 entries), parsing block type out of the
  `graphics\blocks\<name>.mgm` model path. Skips if `Durability` already
  appears in the file. This exists because PWCG doesn't set durability
  per-block the way the user wants, and the authoritative values were
  reverse-engineered (see `utils/durability.sh` below) from what the game's
  own resaver assigns.
- **01_no_bridges.sh** — opt-in (`REMOVE_BRIDGES=true`), deletes bridge
  objects via an `ed` global-delete.
- **01_normandy_map.sh** — PWCG and the in-game GUI disagree on map names
  (`normandy` vs `normandy-summer`); this patches `GuiMap`. (There's a related
  fix a few lines later for Bodenplatte/Rheinland naming — see
  `PWCGMAP` below.)
- **01_no_spotters.sh** — always sets `Spotter = -1;` (disables the spotter
  aircraft/unit feature).
- **01_vwp_radius.sh** — widens the "Virtual War Plan" check-zone activation
  radius (hardcoded game default `20000`) to `VWP_RADIUS_OVERRIDE`.
- **01_wind.sh** — non-essential (`shouldHalt=false`). Looks up the home
  airfield's takeoff heading from `AirfieldLocations.json`, then picks a new
  wind heading randomly from a cone roughly downwind of that heading (70%
  chance of a "narrow" ±45°-ish cone, 30% chance of a wider one; an
  `INVERT_WIND_HEADING` per-campaign flag flips which end of the runway is
  considered takeoff). It rewrites the `WindLayers` MCU heading, appends a
  "Wind: from X at Y m/s" line to the mission briefing subtitles, and rotates
  every `villagesmoke` / `city_fire` / `city_firesmall` smoke-emitter object
  to match (since those don't auto-orient to wind).
- **02_tac_codes.sh** — assigns 2-letter/digit squadron "tactical codes"
  (`TCode`/`TCodeColor`) to planes based on pilot name, using a per-campaign
  `pilot-code-map.csv` (name substring → code) and a `tac_code_pattern`
  printf-style template (via Perl's `printf` for full `printf(3)` semantics).
  Matching is substring-based and case-insensitive. Non-essential
  (`shouldHalt=false`). Its header comment describes a more ambitious design
  (auto-prune dead pilots, auto-assign codes to new ones) that was never
  finished — today it just logs `pilot not configured: <name>` and leaves
  unmapped pilots alone.
- **03_leader_skin.sh** — opt-in (`leader_skin_override`/
  `leader_tcode_override`), forces the flight leader's skin/tac-code —
  handy for giving the player's AI wingman-leader (or similar) a consistent
  look.
- **04_escort.sh** — the most complex component. Only runs for missions whose
  subtitles indicate an escort flight. It surgically rewrites the generated
  escort logic (which it clearly considers unreliable — see Bugs below): it
  reads IDs/positions out of the existing MCUs via `ed`, builds a hexagonal
  "ring" of waypoints for the escort to orbit around the rendezvous point, and
  inserts a bunch of new trigger/timer/check-zone MCUs to: force the escort to
  hold the ring at the rendezvous, force-complete the player's waypoints once
  rendezvous is reached, and (if the player isn't themselves on the escorted
  side) return the escort to orbit its origin afterward. It also appends new
  numbered subtitle entries used by the debug `MCU_TR_Subtitle` nodes it
  inserts, and widens the rendezvous check-zone radius (`RADIUS`, default
  3000m).
- **05_timers.sh** — spreads flight takeoff times out over time so AI flights
  don't all launch simultaneously. Controlled by `TIMERS_B`/`TIMERS_A`/
  `TIMERS_N` (bucket size, offset, bucket count — see `default_env.sh` for the
  bucketing math). The player's and escort's own flights are exempted. Besides
  delaying the "Mission Begin Timer," it has to rebuild the VWP (Virtual War
  Plan) check-zone activation chain per flight so the CZ doesn't activate
  before the delayed flight has actually spawned — it inserts a small state
  machine (retry timer + exclusion timer + deactivate/reactivate MCUs) per
  affected flight.
- **50_pause.sh** — opt-in (`PAUSE_FOR_EDITS=true`), just blocks for a
  keypress so you can manually edit the mission file mid-pipeline before later
  components (notably the resave step) run.
- **74_artillery.sh** — rigs every artillery piece (`graphics.artillery`
  objects) so it can't be destroyed by small-arms/strafing fire, only by a
  bomb: it spawns two invisible collocated "fake blocks" (one high-durability
  "Hard", one zero-durability "Soft") plus a timer/damage-command chain that
  makes the gun briefly vulnerable, "flees" (zero-damage knockback?) and then
  invulnerable again in a ~140ms window, triggered off the fake blocks' death
  events — essentially emulating a damage-threshold mechanic the base
  game/MCU set doesn't support directly.
- **75_debug.sh** — opt-in cleanup; when `DEBUG` isn't `"true"`, disables
  (`Enabled = 0`) all the "DEBUG" `MCU_TR_Subtitle` nodes that other
  components (escort, timers) insert for troubleshooting, so normal play
  doesn't see debug subtitles.
- **98_resave.sh** — runs the game's own `MissionResaver.exe` against the
  mission (needs `unix2dos` first, since the tool presumably expects CRLF).
  This presumably normalizes/validates the file and is why `01_*` components
  must run *before* it (per commit "Relocate artillery to after manual
  modifications" and "Reorder resave and pause operations" — ordering here
  has visibly been fiddled with over time).
- **99_update_sds.sh** — opt-in-by-location: only applies if the mission file
  actually lives under the game's `Multiplayer/` directory. Points the
  dedicated-server `.sds` config at this mission and at the machine's LAN IP
  (preferring a non-`192.168.*` adapter, falling back to one that is), then
  moves the original mission out to a `trash/` folder.

## Supporting pieces

- **default_env.sh** — defaults: auto-detects `MAP` from the mission's
  `GuiMap` field; defines the takeoff-time smearing parameters consumed by
  `05_timers.sh`; sets a default `VWP_RADIUS_OVERRIDE`. Also computes
  `PWCGMAP` (not in this file, actually in `core.sh`) to translate PWCG's
  internal Rheinland→Bodenplatte map-name mismatch.
- **data/durability.csv** — ~900-row `block_name,durability` table, the
  "ground truth" database block_durability pulls from.
- **utils/durability.sh** (+ `.bat` launcher) — a separate drag-and-drop tool,
  *not* part of the main pipeline. Scrapes `Durability`/`Model` pairs out of
  an already-resaved mission file (i.e. after the game engine has assigned its
  own defaults) and merges them into `data/durability.csv`, growing the
  database over time as new block types are encountered. Explicitly strips out
  `fake_block` (the synthetic block used by `74_artillery.sh`) since it's not
  a real game asset.
- **vorus/** — standalone `.Group`/`.eng` file pairs (`CityAttack`, `Column`,
  `StalArtilleryAttack`, `StalRiverCrossing`, `StalRocketAttack`,
  `StalTankBattle`, `StalTankColumn`, `Train`). These are *not* referenced by
  any script — they're prefab mission-editor "Group" blocks (MCU object
  trees) meant to be imported by hand into the full mission editor (the name
  likely refers to the "Vorus" mission-editor tooling in the IL-2 community)
  to drop in pre-built ground-war set-pieces (retreating columns, city
  attacks, artillery barrages, river crossings, train traffic, etc.) as raw
  material for hand-built or PWCG-augmented missions. Git history shows these
  are actively tweaked (`bbd5143`, `d425217`, `52498c6`) independent of the
  Bash pipeline.
- **test.sh** — copies fixtures from a (gitignored, so not present in this
  checkout) `sample-missions/` directory into a temp dir and runs `core.sh`
  over each, with `NO_RESTORE=true` so failures don't clobber the fixtures;
  `MU_TEST_MAX` caps how many to run, `KEEP_TEST` preserves the temp dir
  afterward for inspection.
- **.mission file format** — a brace-delimited, Pascal-ish text format
  (`Group { ... }`, `MCU_Waypoint { Index = ...; Targets = [...]; }` etc.)
  that every component manipulates via the line-oriented `ed` editor rather
  than any structured parser — scripts locate things by searching for literal
  field names/values and reading relative to marks (`ka`, `kb`, ...). This is
  brittle by nature (see Bugs) but is the only reasonably scriptable way to
  surgically edit this format from Bash without a real mission-file library.

## Notable design patterns worth remembering

- **Everything is driven off parsed subtitle text, not a real mission model.**
  Flight names, escort relationships, and home airfields are all recovered by
  grepping fixed English phrases out of the `.eng` briefing. There's no
  structured source of this information; it's a side effect of the format
  pipeline.
- **`ed`'s multi-command global syntax (`g/re/cmd1\<newline>cmd2\<newline>...`)
  is used extensively**, exploiting the fact that unquoted Bash heredocs treat
  a trailing `\<newline>` as a line-continuation, so what reads as several
  "lines" in the script is actually one logical `ed` command list. This makes
  the scripts very hard to read without knowing both quirks (ed's global
  command-list syntax *and* Bash heredoc continuation rules) at once.
- **Per-component isolation via subshells** (`( ... )` in the `core.sh` loop)
  means a component's `set -e`/local variables/trap never leak to its
  neighbors, and the only way to signal "abort the whole run" back up is the
  fifo/fd hack.
- **Self-training lookup table**: `utils/durability.sh` and
  `01_block_durability.sh` form a little feedback loop — the resaver's output
  trains the database that's fed back into future resaves.

## Bugs and fragility noticed while reading

Author-acknowledged (in comments):
- `components/74_artillery.sh`: "It's possible to deactivate a gun while it's
  firing, in which case it will continue to fire" (the brief invulnerability
  window doesn't account for mid-fire state).
- `components/04_escort.sh`: the `ECFCT_ID` ("escort-timer-force-complete")
  timer is commented "doesn't seem to work?" — a known-broken piece left in.
- `components/02_tac_codes.sh`: the header comment describes a fuller
  rework (prune dead pilots, auto-allocate unused codes to new pilots) that
  was never implemented; today unmapped pilots are silently skipped with a
  log line, so new pilots never get a tac code until someone edits the CSV by
  hand.

Found independently:
- **`core.sh` underscore-prefix handling can misfire on prefix collisions.**
  `rm "${missionDir}/${missionCore#_}"*` and the following glob
  `"${missionDir}/${missionCore}"*` both do prefix globbing on the mission's
  base name with no word boundary. If a campaign directory contains two
  missions whose names share a prefix (e.g. PWCG's sequential mission
  filenames, "Mission 1" vs "Mission 10"), re-running the `_`-prefixed
  workflow could sweep up and overwrite the wrong files. Also, if the
  non-underscored target file doesn't exist yet, `nocaseglob`/no `nullglob`
  means the `rm` glob fails to expand and `rm` is called on a literal
  asterisk-containing pattern, printing a harmless-but-confusing "No such
  file" error on every first run.
- **Campaign-name detection is fragile.** `core.sh` derives `campaign` by
  taking the first space-delimited token of the mission filename and checking
  it against a directory name. Any campaign whose PWCG-generated filename
  doesn't start with a single-word, directory-matching token (plausible if a
  campaign's display name has no spaces removed, or PWCG's naming changes)
  silently degrades to `campaign=""`, which just silently disables
  campaign-dependent components (`00_campaign_init.sh`, `02_tac_codes.sh`, the
  per-campaign `env.sh` override) rather than erroring — a misconfigured
  install could silently run with none of its customizations applied.
- **`05_timers.sh` excludes the player/escort flight from re-timing using an
  exact-string `comm -3` diff**, while everywhere else in the codebase flight
  names are matched case-insensitively (`shopt -s nocasematch`) or by
  substring. If the subtitle-derived `$PLAYER_FLIGHT`/`$ESCORT_FLIGHT` string
  ever differs from the mission file's `Name = "Flight X"` string in case or
  incidental whitespace, `comm` would fail to exclude it and the player's own
  flight could get a random takeoff delay — exactly what this script is
  supposed to prevent for the player.
- **Silent no-ops on unmatched `ed` patterns.** Several components (notably
  `01_vwp_radius.sh`, matching the literal text `Zone = 20000;`) locate
  targets by exact literal substring rather than by structural parsing, and
  `ed`'s `g` command simply does nothing if zero lines match — there's no
  verification afterward that the substitution actually took effect. If a
  future PWCG/game update changes a default value this logic assumes (e.g.
  the VWP zone default stops being exactly `20000`), the component would
  report `[OK]` while silently doing nothing.
- **`PIPE=$(mktemp -u)` then `mkfifo "$PIPE"`** in `core.sh` is a classic
  TOCTOU pattern (name reserved via `mktemp -u` without creating the file,
  then a window before `mkfifo` recreates something at that path). Harmless in
  this single-user, local-tool context, but worth flagging as the kind of
  pattern that's normally flagged in security review.
- **`01_block_durability.sh` returns failure on any unrecognized block**
  (`no durability for $block`) — a single unknown block type anywhere in the
  mission aborts durability-patching for the *entire* mission (triggering a
  full restore-from-backup, since `shouldHalt` defaults to `true` for this
  component), rather than skipping just that one block. Since the database is
  manually curated by running `utils/durability.sh` after the fact, any new
  DLC/map/block type will hard-fail every mission until someone notices and
  re-runs the scraper.
